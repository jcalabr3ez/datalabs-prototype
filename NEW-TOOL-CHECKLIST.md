# Adding an AI-enabled tool (DL-XX): the checklist

This is the repeatable path from "we should cover X" to a live, answerable,
automated flagship. It is distilled from DL-04, DL-10, and DL-12. The engine
work is the easy part (an afternoon); the data verification is the real work
(days to weeks). Budget accordingly.

## 0. Pick and scope (before any building)

- [ ] Demand evidence: what are visitors asking that we decline today? The
      question log is the input; do not choose tools by intuition alone.
- [ ] One sentence of scope, and the honest exclusions. The exclusions are
      product decisions, not afterthoughts; they become the router's rules
      and the tool's credibility. Every flagship declines advice,
      predictions, and anything its ledger cannot support.
- [ ] Source inventory: for each figure you want to publish, name the
      primary source, its cadence, and whether it is machine-readable
      (API/CSV like NTD), semi-structured (portal files like OIR), or
      editorial (bills and dockets like the atlas). This determines the
      automation tier in step 5.

## 1. The canonical ledger (netlify/functions/dlXX-answers.json)

Conventions every ledger follows:

- [ ] `tool_id`, `as_of` (used by the freshness gate), `scope` (the model
      reads this), and a vintage note saying how the data was built.
- [ ] Source ids: `SRC-XX-nn` (or `SRC-3nn` style), one per source, with a
      `source_id_map` or register describing each. Every figure a model can
      cite traces to one.
- [ ] Series as arrays of labeled objects (`{"m": "2026-06", "v": 26288869}`
      style), not bare tuples; page projections are generated, ledgers are
      for reading.
- [ ] A `derived` block: precomputed rankings, extremes, counts, and trends,
      with a note telling the model to prefer them over its own arithmetic.
      This is where answer reliability comes from.
- [ ] Verification standard: every figure recomputed from the primary
      source through two independent paths where possible; anything not yet
      verified is flagged pending in copy and in the ledger note, and
      pending flags carry a plan for clearing them (see the LEG-MBTA-01 to
      SRC-302 reconciliation for the pattern).

## 2. The flagship page (dlXX-slug/index.html)

- [ ] House design system: lift the shared stylesheet base (navy #1F3A5F /
      bar #12213A, gold #A87B1F / #E9C46A, green #177245, maroon #8C2532;
      Newsreader heds, Public Sans UI, IBM Plex Mono data), the proto strip,
      dark hero with dateline, exhibits with ex-head numbering and
      srclines, "How this is calculated" folds, the source register as a
      table.reg with cadence / vintage / next release columns, dark footer,
      corrections email datalabs@pioneerinstitute.org.
- [ ] No em dashes anywhere (CI enforces this).
- [ ] Embedded data lives between `/* DATA:BEGIN name */ ... /* DATA:END
      name */` markers and is generated by scripts/inject_data.py from the
      ledger; add the generation stanza there. Hand-authored narrative pages
      (the Florida pattern) instead get sentinel checks in
      scripts/check_style.py so prose cannot silently drift from the ledger.
- [ ] Deep-link handling: the page reads its `#view-...` hash on load and on
      hashchange, switches views, and highlights the referenced entity (see
      tax-atlas applyHash or mbta revealKind). The engine's `link` field
      depends on this.

## 3. The engine (one manifest entry, no ask.js edits)

- [ ] Entry in netlify/functions/tools.js: `id`, `label`, `routerScope`
      (coverage AND exclusions; the router routes or declines on this),
      `dataset`, `modelSlice` (strip page-layout fields and source URL
      lists), `charts` or `views` enums, `viewDefault`, `highlight`
      (validation key + description), `rules` (citation discipline, derived
      preference, ambiguity handling), `link`, `src`.
- [ ] `"ai": true` on the tool in catalog.json.
- [ ] Harness cases in the offline harness pattern (route to the tool,
      shaping, bogus-value coercion, an answerable:false decline).
- [ ] Golden questions in scripts/eval_engine.mjs: 2 to 4 questions that
      must answer with this tool, plus one scope-excluded question that
      must decline or route. This is what makes future prompt edits safe.

## 4. Freshness

- [ ] Add the ledger to RULES in scripts/check_freshness.py with a max age
      matched to the publisher cadence and one line of why.

## 5. Update automation (pick the tier the sources allow)

- [ ] Machine-readable sources: a scripts/refresh_dlXX.py in the
      refresh_dl12.py mold (fetch, recompute, sanity-check, never push) plus
      a monthly/quarterly workflow opening a PR.
- [ ] Semi-structured or editorial sources: a scripts/dlXX-research-pass.md
      runbook in the dl04/dl10 mold, run locally in Claude Code; the
      freshness gate is the reminder.
- [ ] Either way: the automation NEVER pushes to main. PRs get human review;
      merging deploys.

## 6. Launch checks

- [ ] `python3 scripts/inject_data.py` twice (second run says "everything
      in sync").
- [ ] `python3 scripts/check_style.py` and `python3 scripts/check_freshness.py`.
- [ ] Offline harness passes; pages render in a browser, including the
      deep link from a stubbed engine answer.
- [ ] After deploy: run the eval against the live site
      (`SITE_URL=... node scripts/eval_engine.mjs`), and ask the new tool's
      golden questions by hand once.
- [ ] Add the tool to the front-door desk only if it has a live number
      worth leading with; desk stats must be generated from the ledger
      (see DL04D), never typed into copy.

## What this list deliberately keeps hard

Verification is the product. A tool that ships faster by skipping the
two-path recompute, the source register, or the pending flags is not a
smaller version of a DataLabs tool; it is a different product. When
timelines squeeze, cut scope (fewer figures, fully verified), never rigor.
